This release covers Iterations 177–194 (see `CHANGELOG.md`). It is the release that ships the coverage expansion prompted by the AlgoScalperApi requirements audit: six new skills closing the gaps between generic Rails guidance and the engineering problems of streaming feeds, durable order state, financial arithmetic, market data, and LLM integration — plus the recorded-model campaign, the AI code review suite, and the benchmark campaign expansions that preceded them.

### Six new skills from the coverage audit (Iterations 189–194)

The audit mapped a complex Rails trading application's engineering problems against this pack and identified six boundaries that existing skills referenced only obliquely. All six ship in this release, each with references, adversarial routing cases, evaluation families, and registered system tests:

1. **`rails-external-stream-ingestion`** (Iteration 189) — the consuming side of external streaming feeds: provider WebSocket/broker clients, connection ownership and supervision, heartbeats, reconnection with explicit registry replay, bounded buffering and backpressure, duplicate suppression, event-time versus processing-time discipline, freshness/staleness contracts, gap detection, and unavailable-feed failure semantics (stop, degrade, alert, reject). Deliberately separated from Action Cable, which owns Rails' serving side.

2. **`rails-state-machine-engineering`** (Iteration 190) — durable workflow state as a contract: transition tables, guarded single entry points, transition authorization, append-only audit history, locking by contention, duplicate and out-of-order event handling, side-effect sequencing with durable intent, recovery windows with reconciliation, and test matrices generated from the table. Adds the `state-transition-guard` and `state-machine-testing` patterns.

3. **`trading-execution-safety`** (Iteration 191) — order placement through external execution venues: durable intent before side effects, deterministic client order IDs (ClOrdID discipline), duplicate prevention at database/guard/venue layers, submission versus acknowledgement versus fill as separate facts, partial fills as accumulating increments, ambiguous outcomes treated as probably-executed and resolved by reconciliation, paper/live separation behind default-off gates, and fail-closed risk gates. Introduces the `trading` family.

4. **`ruby-financial-data-integrity`** (Iteration 192) — money and ledger arithmetic: exact representation at every boundary (integer minor units or scale-fixed `BigDecimal`), decimal precision/scale sized for aggregate sums, named rounding decisions, largest-remainder allocation, double-entry invariants, atomic balance updates, posting idempotency on the event identity, fee/PnL arithmetic with sign conventions, continuous invariant checks, and scheduled external reconciliation.

5. **`trading-market-data-and-backtesting`** (Iteration 193) — the measurement infrastructure: OHLCV contracts with pinned timestamp semantics, gap detection against session calendars, timeframe alignment, IANA timezone and DST discipline, as-of instrument masters, look-ahead prevention through one strictly-before as-of primitive, conservative fill models with fees and slippage, deterministic replay with digest comparison, and out-of-sample evaluation with spent-once holdouts.

6. **`ruby-llm-integration`** (Iteration 194) — model calls as a bounded, untrusted dependency: one adapter boundary, timeouts and bounded retries by failure class, token/cost budgets, schema-validated structured output, prompt-injection boundaries, tool-call authorization through deterministic policy, observability without prompt logging, graceful degradation with core paths independent of the model, and the rule that model output proposes but never substitutes deterministic guards.

Each new skill routes away from its nearest existing neighbor with adversarial routing cases (broker WebSocket vs Action Cable, order FSM vs AASM trivia, AI proposals vs deterministic guards), so an agent changing a feed client or an execution path activates the right contract instead of adjacent generic advice.

### AI code review suite (Iteration 188)

`ai-code-review` expands into a risk-based review suite for single files, PRs/diffs, and whole-repository audits, with a three-pass review protocol, risk-oriented checklists, evidence-based reporting, reviewer training and ledger references, and findings/context helper scripts.

### Recorded model campaign (Iteration 187)

The `recorded-model-campaign-v1` recording set captures a real model's workspace edits for seven evaluations in both paired configurations, with a replay adapter that verifies prompt digest, workspace manifest, and materialized skill/pattern fingerprints before replaying, and refuses tampered workspaces. The recordings state their provenance explicitly: they validate the adapter protocol, runner, and verifiers end to end, and are not a neutral measurement of third-party model difficulty.

### Benchmark campaign expansion (Iterations 181–186)

The distributed-systems, reliability, event-driven-messaging, and database-engineering campaigns added eleven deterministic pure-Ruby fixtures with pristine references and dedicated verifiers (transactional inbox/outbox, saga compensation, bulkheads, circuit breakers, load shedding, SLO budgets, messaging contracts, and the transaction-isolation fixture simulating PostgreSQL semantics). Every evaluation file in the public corpus is now campaign-covered or explicitly classified `coverage: static-only`.

### Book-grounded skills and earlier iterations (Iterations 177–180)

Iteration 178 landed the book-grounded Ruby and Rails front-end skills; Iteration 179 closed four depth gaps from the advanced Rails coverage audit (Sidekiq adapter, and three other single-skill reference expansions); Iteration 180 hardened callback-cascade verification with per-condition grading and pinned control outcomes.
